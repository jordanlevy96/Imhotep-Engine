# Author VaporQube through the Editor

2026-10-09. This target supersedes the template-first priority in the initial Editor audit.

## User-visible outcome

From the Editor, create a scene using the existing cube/shader assets, attach the VaporQube Lua scripts, edit their settings and the HUD, save, Play, Stop, reopen, and continue editing. Gameplay code remains Lua: authoring through the Editor includes editing scripts, not replacing Tetris rules with engine features or a visual-programming system.

The first usable milestone is a smaller loop: open a copy of VaporQube's authored YAML, select `light`, change its position, save, launch that copy, stop it, reopen, and see the authored change. Generated pieces, ghost blocks, score and board state must never appear in the saved authoring document.

## Real authoring operations and current gaps

Paths below are relative to the repository root; findings are source-verified, not claims of observed UI behavior.

| Authoring operation | Existing Tetris evidence | Editor/engine gap |
|---|---|---|
| Choose project resources, startup scene and HUD | `res/games/vaporqube/conf/settings.yaml` points to scene and HTML/CSS/Lua UI | Editor hardcodes its config/test scene and template directories; game HUD is outside its template manager roots |
| Create named scene objects | `scenes/Scene.yaml` defines light, GameGrid, SkyBackground, TiledBackground, FlyingProps | Registry creates entities, but Editor exposes no create/delete/rename document operations |
| Assign mesh, shader and lighting | Light uses `Basic.shader`/`cube.obj`; GameGrid uses `OutlinedCube.shader`/`cube.obj`; Tetrimino attaches lighting | Assets exist and rendering works; no component/asset picker or resource validation panel |
| Edit transforms | YAML loads position, scale and color; inspector also edits rotation in memory | No persistence before this iteration; Registry loader does not read rotation, so defining its serialized representation is still needed |
| Compose modules | Scene `scripts` lists Constants, Data, Tetrimino, Logic, Input; modules declare roles/requirements/capabilities | SceneLoader validates contracts while executing Lua; Editor needs authoring diagnostics without treating load as safe static validation |
| Attach script and properties | GameGrid/background LuaScript components; FlyingProps scalar settings | Registry looks up the component table by entity name and passes properties as strings; arbitrary instance naming/typed fields are not supported cleanly |
| Write gameplay rules | `GameGrid.lua`: board, collision, movement, DAS, rotation, hold, ghost, line clear; `Tetrimino.lua`: entity factory/hierarchy/tween | Game-specific Lua code, already supported by engine; missing script editing/diagnostics workflow in Editor |
| Define input | `GameInput.lua` routes literal key names; `GameGrid.lua` polls LEFT/RIGHT | YAML keyMappings do not describe the actual gameplay controls; an input panel must not imply they do |
| Author HUD and menus | `ui/templates/game.html`, `styles/game.css`, `state/game.lua`; GameLogic updates UI values | Current template fields/selector lack complete control wiring and correct game resource roots |
| Play and stop | Game initializes the configured scene and runs ScriptSystem; Editor skips ScriptSystem | No Play/Stop lifecycle; loading another scene into existing singleton state is not an isolated preview |
| Save and reopen | Runtime blocks are created/destroyed by GameGrid/Tetrimino Lua | Must persist authored scene/resources, not dump Registry; Registry IDs are monotonic process-local IDs |

Existing gameplay tests provide useful regression evidence (constants, shape data, lifecycle/UI, key routing, collision), but some scoring coverage duplicates formulas. They do not prove the complete game can be authored or played from Editor controls.

## Implemented first portion

`SceneDocument` in `include/editor/SceneDocument.h` and `src/editor/SceneDocument.cpp` now provides headless Load, SetPosition and Save. It reads authored YAML without importing Lua, creating ECS entities, or opening graphics. Edits retain unrelated YAML values, including unknown component types and custom fields. Names must be unique/nonempty for this limited operation; this does not change the runtime loader's existing acceptance rules.

Save writes a sibling temporary file and renames it into place after successful serialization/write. A reserved sibling directory prevents overlapping saves using the same temporary path. Failure retains dirty state and the existing destination. This is not a crash-durable transaction: no fsync, external-change detection, multi-resource transaction or recovery from abandoned reservation directories is implemented. YAML comments/formatting are regenerated by yaml-cpp; field values are preserved.

`editor.scene-document` tests the real VaporQube scene round trip, missing object/nonfinite rejection, malformed reload preserving edits, unavailable destinations, existing-save reservation, failed replacement cleanup, duplicate names and unknown fields. All six headless tests pass. Open, Save, Save As and authored position editing are now connected to the existing Editor shell through `SceneSession`. Create/add-object/component-reference assignment has since been added in the separate slice below. Undo/MCP remain unimplemented; the Play slice below adds an owned runtime process.

## Shared operations and eventual AI interface

A small shared document/operation layer is justified by current direct mutations in Editor callbacks, absent serialization and runtime singleton ownership. Grow it from concrete operations above; do not build a generic command bus first. UI callbacks and a later AI adapter should call the same validation/mutation/save functions.

Before exposing mutation to AI:

- Introduce persistent authored object IDs with an additive YAML field and migration for existing scenes. Runtime EntityID and editable names are unsuitable lasting references. Current name-based document editing is intentionally limited; rename/reorder/remote handles are deferred.
- Add document revision checks and grouped undo/redo with before/after values. A drag or typed field commit should be one undoable edit, not one history entry per frame/character. Save establishes a clean revision; undo back to it clears dirty state.
- Return structured validation errors tied to document/object/property. Separate YAML/schema/reference checks from executing script contracts; script execution belongs in controlled validation/play.
- Bound resource paths to the opened project, report proposed changes, serialize operations onto the editor thread when touching runtime/UI state, and reject stale handles. Read-only inspection should not execute Lua.

MCP would expose operations such as inspect scene/resources, create object, assign component/script, set property, validate, save, undo/redo, start/stop owned play process and read diagnostics. No unrestricted shell/Lua-eval tool is needed for that interface. MCP specifies discoverable tools and typed input/output schemas, which can wrap these operations once they are dependable ([official tool specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). A local stdio adapter is a later option without opening a network listener ([official transport specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)). No MCP server, credentials or network access was created.

## Integrated controls and review (current slice)

The scene sidebar now has a path field, Open, Save and Save As, the current file, dirty state and errors. Ctrl/Cmd+O opens the path field's value; Ctrl/Cmd+S saves the current document. An attempted dirty Open is blocked; the explicit Discard and Open action still preserves edits if the candidate fails. Save As updates the current path only on success. Close/ESC is blocked while scene edits or rejected position drafts remain. Selection changes restore rejected drafts to authored values. Rotation and scale are read-only for this position-only slice.

Position edits update the document first and then its preview entity. Other coordinates retain their authored precision. Invalid drafts survive focus changes and prevent Save until corrected or reverted by selecting an object again. Enter now clears focus through the actual key-event path.

Independent code review identified silent invalid-asset acceptance and invalid drafts escaping validation after focus changes. Both were fixed and re-reviewed without further blocking findings. Shader parsing now rejects missing sections/unsafe preamble content; shader compile/link failures throw and release allocated GL objects. Mesh loading rejects failures, empty faces and invalid/missing normal indices before unsafe reads or GPU upload. This is required for candidate-preview rejection to preserve the open scene. Tests exercise actual CPU parse failures and simulated driver compile/link failures; they do not validate a real GPU or window.

## New scene and reference assignment slice

The reviewed Open/Save/position foundation is preserved in local commit `975c181` (`feat(editor): edit and persist authored scene positions`). The creation/assignment slice is preserved in local commit `d306c72`.

The scene sidebar now provides a scene name and New/Discard and New, plus an object name and Add Object. Newly added objects are selected automatically. New scenes are dirty and have no current save destination; Save As writes the path field. No rename operation is offered, so creating or assigning a script never silently changes an object name.

The selected-object inspector has separate Mesh and Lua assignment modes. Mesh accepts existing `.shader`/`.obj` references inside the resource shader/model directories. Lua accepts an existing resource-relative `.lua` path and optional shader/model properties. Render references and Lua properties use separate input buffers even when both components coexist. Switching assignment mode clears input focus. Blank optional Lua fields retain existing properties; arbitrary properties and removal are outside this slice.

Lua coupling is explicit: the current runtime looks up a global table by entity name after executing its component script. This slice conservatively requires script filename stem to match the object name (e.g. `GameGrid` and `games/vaporqube/scripts/GameGrid.lua`) and explains that the script must export that global table. The filename rule is an authoring restriction, not proof of a Lua export. No scripts are executed or syntax/dependency-validated by attachment. Existing VaporQube GameGrid/background scripts follow this convention; local-return-only scene modules must not be treated as interchangeable entity scripts.

New/Add/Assign use the same staged preview boundary as Open. Candidate document changes are cloned, validated and projected before publication. Failed resource or preview preparation preserves the original document, current path, selection and dirty state. Duplicate object names, invalid names, absent resources, absolute/out-of-root resource references, ambiguous duplicate component entries and conflicting Lighting/render assignment are rejected. Unknown YAML/component properties are retained.

A headless test creates an authored scene, adds `light` and `GameGrid`, assigns Basic/cube and GameGrid/OutlinedCube/cube references, edits the new unsaved scene, saves and reopens it. Additional assertions cover failed staging, duplicate/name-coupling errors, unchanged assignments, unknown-property preservation and independence of render/Lua component data. Independent review found the mixed-field issue described above; it was corrected. Editor build and all six headless tests pass with single-job builds. Hands-on UI/GPU verification is still pending; no permission retries occurred.

The creation slice alone is not playable Tetris. Ordered modules, capabilities and Play/configuration selection are implemented in the next slice below. No new product decision was needed for the bounded creation/assignment subset. Stable IDs, rename semantics, broader script binding and undo remain explicitly deferred.


## Modules, configuration selection and owned Play

The Modules tab edits the existing ordered top-level `scripts` sequence, `capabilities.ui`, `capabilities.input`, and `strict` fields. Add/reorder/remove operations use `SceneSession` and preserve unknown YAML fields. Assignment requires unique existing resource-relative Lua files. It does not execute scripts or verify their dependency contracts. Five module rows per page keep the controls bounded; Scene, Game and Modules tabs clear hidden input focus when switching.

The Game tab selects an existing game YAML (default field: `games/vaporqube/conf/settings.yaml`) inside the current resource directory. Selection validates the game/window maps, template name and existing HTML/CSS/Lua-state references. It retains the selected configuration separately from the editable path field. This is selection within the current engine checkout, not an arbitrary project-root browser: the runtime currently overrides `game.resourcePath` with PathResolver's `../res/` in development mode. Configuration editing, resource import and game-root relocation remain outside this increment.

Play Saved Scene rejects unsaved documents and invalid position drafts. It revalidates the selected configuration and saved scene, requires the scene inside `res/` and execution from the matching `build/`, then writes a unique `build/.editor-play-*/settings.yaml`. It preserves configuration fields, replaces `game.scenePath` and uses a unique engine log filename. The source game YAML and authored scene are never written by Play. Runtime stdout/stderr are captured in the same generated directory's `output.log`; engine logging still uses the existing `logs/` directory. Generated run files are retained for diagnosis.

`PlaySession` launches the CMake-selected game executable with `posix_spawn`, an argument vector and child working directory. It removes `USER_SETTINGS_PATH` from the child's environment because EngineCore otherwise ignores `--config`. Parent environment remains unchanged. Poll reports exit/signal status and the output path; launch success does not assert that game initialization succeeded. Stop and Editor shutdown terminate/reap only that session's owned child, escalating from TERM to KILL after a bounded grace period. No shell, process-name termination or Editor Lua VM reuse occurs. This implementation supports macOS/Linux; Windows reports unsupported. Linux remains compile/runtime unverified on this Mac.
